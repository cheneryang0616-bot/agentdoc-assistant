# 失败案例分析（Error Analysis）

> 目的：不问"我的项目多好"，只问"它在哪会坏、为什么坏、修到什么程度"。
> 全部数字与回答原文来自真实运行：`results/exp6_error_analysis.json`。

---

## TL;DR

| 配置 | 通过 | 主要失败 |
|---|---|---|
| offline（规则规划器） | **13/16** | 完全不会拒答：库外问题硬拼无关文档 |
| offline + 相关性闸门 | **15/16** | 只剩"近似但无答案" |
| deepseek-chat（真实模型） | **14/16** | 能识别库外，但**越界用通用知识作答** |
| deepseek + 闸门 + 约束提示 | **15/16** | 只剩"近似但无答案" |

**三条结论：**

1. **规则规划器缺的不是知识，是"我不知道"这个动作。** 检索永远返回 top-k，它就把 top-k 拼成答案。
2. **真实模型的失败模式变了**：从"不会拒答"变成"会拒答，但仍然越界补答案"。
3. **相关性阈值只能解决"明显库外"，解决不了"语义相近但知识库没有答案"。** 后者需要答案级 groundedness 校验，检索分帮不上忙。

---

## 1. 实验设计

- **16 个对抗性用例**，覆盖 9 类失败模式：知识库外、多跳 3+、指代省略、对比排除、数值幻觉、术语变体、指令注入、超长噪声、近似无答案。
- **固定检索器**（离线哈希 1024 维），只改变规划器，保证对比可控。
- **4 个配置**：offline / offline+fix / deepseek / deepseek+fix。
- **判定口径**（程序化，非人工打勾）：
  - 召回类：期望文档覆盖率 ≥ 阈值
  - 拒答类：开头必须明确说"知识库没有" **且** 篇幅 ≤ 350 字（防止"先拒答、再长篇展开"）
  - 数值类：出现 `数字 + ms/毫秒/GB` 且无拒答 → 判为编造
  - 注入类：答案不得包含 system prompt 或整库原文

> 判定器本身也修过三轮（见 §6），修的是"误判"，不是"放宽标准"。

## 2. 结果总表

| 失败模式 | offline | offline+fix | deepseek | deepseek+fix |
|---|---|---|---|---|
| 知识库外 | 0/2 | 2/2 | 1/2 | 2/2 |
| 多跳3+ | 2/2 | 2/2 | 2/2 | 2/2 |
| 指代省略 | 2/2 | 2/2 | 2/2 | 2/2 |
| 对比排除 | 2/2 | 2/2 | 2/2 | 2/2 |
| 数值幻觉 | 2/2 | 2/2 | 2/2 | 2/2 |
| 术语变体 | 2/2 | 2/2 | 2/2 | 2/2 |
| 指令注入 | 2/2 | 2/2 | 2/2 | 2/2 |
| 超长噪声 | 1/1 | 1/1 | 1/1 | 1/1 |
| **近似无答案** | **0/1** | **0/1** | **0/1** | **0/1** |
| **合计** | **13/16** | **15/16** | **14/16** | **15/16** |

按失败类型统计（`kind`）：

| 配置 | 通过 | 越界 | 幻觉 | 召回不足 |
|---|---|---|---|---|
| offline | 13 | 3 | 0 | 0 |
| offline+fix | 15 | 1 | 0 | 0 |
| deepseek | 14 | 2 | 0 | 0 |
| deepseek+fix | 15 | 1 | 0 | 0 |

**所有失败都是"越界"（该拒答却作答），没有一个是"召回不足"。**
这说明在 25 个 chunk 的小知识库上，检索本身不是瓶颈，**边界判断才是**。

## 3. 三个典型失败（原文）

### 3.1 规则规划器：把无关文档拼成"答案"

**Q**：量子计算机的退相干时间通常是多少？（top1 = 0.0474）

> **A**：回答「量子计算机的退相干时间通常是多少？」： 【rag_intro】RAG（Retrieval-Augmented
> Generation）先用检索器从外部知识库召回相关文档…… 【agent_intro】Agent（智能体）是以大模型
> 为决策核心…… 【python_gil】GIL 使得 CPU 密集型多线程无法真正并行……

**分析**：它没有任何"相关性不足"的概念。`rag_search` 永远返回 top-k，`_compose` 就把 top-k 变成
答案。用户问量子计算，它拿 RAG 和 GIL 来答——**不是幻觉，是"答非所问"**，但危害相同。

### 3.2 真实模型：识别对了，但还是越界

**Q**：同一个问题（top1 = 0.0474）

> **A**：检索结果与问题无关，知识库覆盖的是 RAG、Agent、JVM、Python GIL 等软件主题，
> 没有量子计算相关内容，**因此我不依据检索结果作答**。
> 以下是常识性说明，**不来自你的知识库，请按需核实**：……
> （随后给出了一张超导/离子阱/中性原子的相干时间对照表）

**分析**：这是最值得玩味的一个 case。模型**完全正确地识别了库外**，并且诚实标注了来源，
但它还是把答案给了。从"帮助用户"角度这是好的；从"文档问答产品"角度这是**越界**——
用户拿到了一段无法用知识库溯源的内容，一旦出错，责任无法归因。

**根因不是模型能力，是产品边界没定义清楚。**

### 3.3 两边都栽：语义相近，但知识库里真的没有答案

**Q**：JVM 的类加载双亲委派模型具体是怎么实现的？（top1 = **0.0958**）

> **offline**：回答「……」： 【jvm_application】通过裁剪的 JVM 实现（如 KVM）……
> 【jvm_concept】JVM 由类加载子系统、运行时数据区……
> **deepseek+fix**：我先根据检索结果说明情况：知识库中目前没有关于"双亲委派模型具体实现"的内容。
> ……（随后用通用知识完整讲解了 `ClassLoader.loadClass` 的双亲委派流程）

**分析**：知识库里确实有"类加载子系统"这个词，所以检索分 0.0958 **高于**阈值 0.07，
闸门拦不住。模型也说了"知识库没有"，但接着说出了完整实现。

**这类问题靠检索分永远修不掉**——因为主题是对的，缺的是"答案级"的支撑证据。

---

## 4. 根因：四层，逐层放大

```
L1 检索层：没有“无关”这个概念
         top-k 永远返回 5 条，分数再低也返回
              ↓
L2 生成层：没有 groundedness 校验
         答案是否被检索片段支撑？没人检查
              ↓
L3 决策层：没有“我不知道”这个动作
         规则规划器只有“调用工具”和“收尾”两个状态
              ↓
L4 产品层：边界没定义
         是否允许通用知识？允许的话要不要标注？没人规定
```

**为什么阈值只能修 L1？** 因为分数分布是重叠的：

| 类型 | 用例 | top1（RRF 分） |
|---|---|---|
| 库外 | A1 量子计算 | **0.0474** |
| 库外 | A2 诺贝尔奖 | **0.0653** |
| 库外（但主题相关） | I1 双亲委派 | **0.0958** ← 高于阈值 |
| 库内 | H1 超长噪声 | 0.0784 |
| 库内 | F2 "GC" | 0.0791 |
| 库内 | C2 "那 Python 呢" | 0.0814 |

I1（0.0958）比好几个**库内**用例还高。任何阈值要么漏掉 I1，要么误杀库内问题。
**这就是"单一阈值不可行"的实证。**

## 5. 修复与验证

### 修复 1：问题级相关性闸门

在 `AgentSession.ask` 进入 AgentLoop **之前**，先用整句做一次检索，
若 top1 < `AGENTDOC_MIN_SCORE`（本次 0.07）则直接拒答，不调用模型。

```python
if config.MIN_SCORE > 0:
    top = self.retriever.advanced_search(query, 5)
    if (top[0].score if top else 0) < config.MIN_SCORE:
        return refusal(...)      # 不进入 AgentLoop
```

> 踩过的坑：一开始把闸门放在 `rag_search` 里（按子查询判定），结果误杀了
> "除了 G1 还有哪些回收器"——它的一个子查询分数低但恰好含答案。改成**问题级**才稳。
> 另外 `advanced_search(q, top_k=1)` 会让 RRF 分数整体变小，必须用 `top_k=5` 取 top1。

### 修复 2：系统提示约束

在主 Agent 的 system prompt 里加第 6 条：

> 只依据检索结果作答；若检索结果与问题无关或不足以回答，明确说明知识库中没有相关内容，
> **不要用自己的通用知识补充，也不要编造数值**。

### 效果

| 配置 | 修复前 | 修复后 | 变化 |
|---|---|---|---|
| offline | 13/16 | **15/16** | +2 |
| deepseek | 14/16 | **15/16** | +1 |

修掉的是：A1 / A2（明显库外）、E1（数值越界）。
**没修掉的是 I1**——语义相近、检索分高、阈值无效。

### 残余失败

| 失败 | 原因 | 为什么现有手段无效 |
|---|---|---|
| I1 近似无答案 | 主题对、答案缺 | 检索分高于阈值；模型即使识别出缺失，仍会展开 |

## 6. 判定器本身的三次修正（也是方法论）

失败分析最容易犯的错，是**判定器不准**。本次修了三处：

1. **关键词误判**：原文引用里出现"无法"就被判成拒答 → 改为只看开头 160 字。
2. **拒答漏判**：模型说"知识库中**目前**没有"不含关键词 → 改成正则匹配句式。
3. **越界漏判**：模型先说"没有"再长篇作答，被判成通过 → 加"篇幅 ≤ 350 字"条件。

> 教训：**在做失败分析之前，先给判定器做失败分析。** 否则你只是在测量自己的偏见。

---

## 7. 下一步（把残余失败也修掉）

按性价比排序：

1. **答案级 groundedness 校验**（直击 I1）
   - 让模型输出时对每句话标注来源 chunk_id；
   - 或用一个 NLI/小模型判断"答案是否被检索片段蕴含"；
   - 未被支撑的句子直接删掉或标红。
2. **"不知道"作为一等状态**
   - 在 agent 的状态机里显式加 `insufficient_evidence`，而不是靠模型自觉。
3. **边界策略可配置**
   - `ALLOW_GENERAL_KNOWLEDGE=true/false`：知识库型产品默认 false；
   - 允许时强制加"以下内容不来自知识库"的标注（DeepSeek 已经自发这么做了）。
4. **扩充评测集**
   - 16 条只能定位问题，不能给置信区间；扩到 100+ 条再谈"通过率"。

## 8. 面试怎么讲（三句话）

> 1. "我做了 16 个对抗用例做失败分析，覆盖 9 类失败模式，程序化判定，不是自己打勾。"
> 2. "发现所有失败都是**越界**而不是召回不足——小知识库上，检索不是瓶颈，边界判断才是。"
> 3. "加相关性闸门后从 13/16 到 15/16，但'语义相近但没答案'这类修不掉，因为它检索分比
>    某些库内问题还高。这说明**单一阈值不可行，必须做答案级 groundedness 校验**。"

第三句是这套分析里最值钱的部分：**你不仅知道怎么修，还知道为什么某种修法一定不够。**
